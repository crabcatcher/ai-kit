## Область применения

Решение: `ai-kit` — бэкенд-стартер. Слои, миграции и владение объектами остаются формой по умолчанию; фронт и мобильное приложение не размывают текущие шаблоны, а получают отдельный доменный профиль. Триггер появления такого профиля — реальный второй пилот: без него обобщение будет гаданием.

## Шаг 6: генератор `init`

Сделано (`docs/generator.md`):

- профиль собирается из базового профиля, проб и ответов; `unknowns` остаются, известные поля из них убираются;
- TOML пишется стандартной библиотекой, порядок разделов фиксирован;
- документы рендерятся в памяти и пишутся только после успешной проверки;
- фрагменты адаптера вставляются по `target` и сохраняют ручное содержимое маркеров при повторном запуске;
- сгенерированные фрагменты: канон K, правила A и P, строки «нет гейта», список правил для `AGENTS.md`;
- `--dry-run` и проверка выхода за каталог проекта.

Что осталось без источника данных: `generated:features`, `generated:debt`, `generated:incidents` — разделы удаляются до появления источника; это записанный пробел, а не забытая функция.

## Шаг 7: валидатор `doctor`

Сделано (`docs/doctor.md`):

- встроенные проверки: профиль, манифест, шаблоны, документы, подстановки, ссылки, маркеры, пустые разделы, покрытие реестра и техдолга;
- внешние гейты: доступность бинаря, диапазон версий, запуск без shell, коды `0/1/2/3`, заглушка не считается успехом;
- запуск гейтов только по `--gates`; без флага — видимое предупреждение, а не тишина;
- отчёт человеку и `--json`, коды возврата `0/1/2`;
- конформанс-корпус из 14 фикстур, 100% прохождения;
- проверки добавлены в `tests/test_doctor.py`, `tests/test_gates.py`, `tests/test_diagnostics.py`.

Что осталось за шагом: замена существующей проверки документов на единую реализацию набора. Условие перехода — зелёный корпус; сам переход делается отдельно на пилоте, а не в этом наборе.

## Открытый анализ: зрелость проекта

Решение не принято; шаги 6–7 реализованы без ветвлений по зрелости, поэтому генератор и проверки одинаково работают с тем, что доказано или сказано.

| Состояние | Что есть | Вопрос к анализу |
|---|---|---|
| новый | кода и документации нет | нечего анализировать: набор создаёт скелет, а факты остаются `unknown` до первого кода |
| развивающийся | код есть, документации нет | работает текущий маршрут: пробы по коду, вопросы о решениях |
| развивающийся с документацией | код и документы есть | что делать с существующими документами: переносить факты, оставлять как есть или заменять |

Вопросы, которые надо закрыть до правок:

1. считается ли существующая документация доказательством (`probe`) или только ответом (`answer`);
2. переносятся ли существующие документы в структуру набора или остаются рядом со ссылкой;
3. что делать с расхождением: код — источник истины, но старый документ может хранить решение, которого в коде нет;
4. нужен ли отдельный режим `init` для каждого состояния или одно поведение с разными ответами на вопросы.

Пока это только план: ни одна из веток не реализована, тесты и шаблоны состояний не знают.
