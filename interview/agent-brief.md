# Брифинг: агент поднимает набор документов

Ты поднимаешь документацию проекта по набору `ai-kit`. Результат работы — не «красивые документы», а профиль с доказанными фактами, набор документов из шаблонов и отчёт о том, что подтверждено, что спрошено и что осталось неизвестным.

## Порядок

1. **Разведка (только чтение).** Найди манифесты, каталоги исходников, конфигурацию проверок, схему хранения, файлы непрерывной проверки, существующую документацию.
2. **Таблица фактов.** Для каждого факта: что нашёл, где искал, путь-доказательство, провенанс.
3. **Профиль.** Заполни `profile.toml` только из таблицы.
4. **Вопросы.** Один батч, не больше двенадцати, по банку `interview/questions.toml`. Не спрашивай то, что уже доказано; слоты, дедупликацию и формат ответов задаёт `docs/interview.md`.
5. **Генерация.** Собери документы из шаблонов генератором (`docs/generator.md`); фрагменты адаптера — только между маркерами, ручное содержимое маркеров сохраняется.
6. **Проверка.** Прогони валидатор и покажи отчёт.

## Что считается доказательством

| Факт | Где искать | Провенанс |
|---|---|---|
| версия рантайма и фреймворков | манифест и лок-файл зависимостей | `probe` |
| каталоги исходников | структура репозитория | `probe` |
| команды проверок | манифест, конфигурация проверок | `probe` |
| хранилище и его версия | конфигурация подключения, схема | `probe` |
| непрерывная проверка | файл конвейера | `probe` |
| назначение проекта | документация, описание репозитория | `answer` |
| границы проекта | человек | `answer` |
| слои и зависимости | структура каталогов и импорты | `probe` или `answer` |

Версия заполняется **только** из `probe` и только с путём-доказательством. Версия, названная человеком, — не факт: это `unknown` плюс вопрос.

Пробу выполняет адаптер автоматически или агент вручную — провенанс определяется доказательством, а не способом. Прочитал манифест и указал путь — `probe`; услышал от человека — `answer`.

## Жёсткие правила

- Ничего не выдумывать. Нет доказательства и нет ответа — `unknown`, а не «вероятно».
- Не заполнять версию из памяти, из названия проекта или из «обычно так бывает».
- Один батч вопросов, не больше двенадцати; «не знаю» — допустимый ответ и уходит в `unknowns`.
- Не описывать архитектуру, которой нет. Если слоёв нет — так и записать: «границы не зафиксированы».
- Названия технологий живут в профиле и адаптере, не в ядре.
- Не удалять секции шаблона «на потом»: пустая секция — видимый пропуск, её надо закрыть фактом или вопросом.

## Если доступа к репозиторию нет

- попроси пути манифестов и каталогов, не угадывай;
- заполни только то, что сказал человек, с провенансом `answer`;
- всё остальное — в `unknowns` с конкретным вопросом;
- в отчёте скажи прямо: «пробы не выполнялись, факты о стеке не подтверждены».

## Архитектура схематично

Даже без деталей архитектура должна быть видна:

- назначение и границы;
- слои: имя, ответственность, от чего можно зависеть;
- направление зависимостей: только в разрешённую сторону, обратное ребро — нарушение;
- внешние системы: зачем и кто владеет контрактом;
- решения: что выбрали, почему, что отвергли;
- «что не разобрано» — обязательный раздел, а не признание провала.

Шаблон — `templates/architecture.md.tpl`. Если слой не подтверждён, он не выдумывается: раздел остаётся скелетом, а вопрос — в `unknowns`.

## Чек-лист перед сдачей

- [ ] у каждого факта о стеке есть путь-доказательство;
- [ ] ни одной версии из `answer`;
- [ ] вопросов не больше двенадцати, батчем;
- [ ] все неизвестные — с конкретным вопросом;
- [ ] слои либо подтверждены, либо явно названы не зафиксированными;
- [ ] фрагменты адаптера только между маркерами;
- [ ] валидатор прогнан, отчёт приложен.
