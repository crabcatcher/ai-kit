# Генератор init

Шаг 6 плана. Генератор обслуживает бэкенд-стартер: собирает профиль из проб и ответов, рендерит документы из шаблонов и заполняет сгенерированные фрагменты. Реализация — `ai_kit/init.py`, запись TOML — `ai_kit/toml_writer.py`, строки реестра — `ai_kit/rules.py`.

## Карта разделов

| Раздел | О чём |
|---|---|
| 1 | входы и выходы |
| 2 | сборка профиля |
| 3 | рендер документов |
| 4 | фрагменты адаптера |
| 5 | сгенерированные фрагменты |
| 6 | правила K, A, P |
| 7 | безопасность, повторный запуск, коды возврата |
| 8 | границы шага |

## 1. Входы и выходы

| Вход | Обязателен | Что даёт |
|---|---|---|
| профиль | нет | базовые факты и решения; без него проект собирается с нуля |
| адаптер | нет | пробы, вопросы, команды, правила A, фрагменты документов |
| ответы | нет | то, что не доказано файлами; TOML или JSON |

Выход — профиль (по умолчанию `profile.toml`) и все документы манифеста (по умолчанию 17). Генератор не коммитит и не запускает команды проекта.

Три режима интервью:

| Режим | Как | Кто спрашивает |
|---|---|---|
| пакетный | `--answers <файл>` | никто, ответы готовы заранее |
| агент | `interview --plan --json`, затем `--answers` | агент в чате |
| консоль | `--ask` | скрипт по одному слоту |

Без профиля и без ответов запуск запрещён, кроме `--ask`: пустой профиль не проходит схему. Без ответов, но с профилем — работает: неизвестное просто остаётся неизвестным.

## 2. Сборка профиля

1. базовый профиль читается как TOML; отсутствующий — пустой объект;
2. пробы выполняются по каталогу проекта, ответы применяются после проб;
3. структурные поля набора получают значения по умолчанию: `schema_version = "1"`, `docs.language = "ru"`, `docs.dir = ".project"`, пустые `stack` и `tests`; это оформление набора, а не факт о проекте;
4. неизвестные из ответов объединяются с прежними: свежая запись заменяет старую по полю, запись о поле, которое уже известно, удаляется;
5. профиль проверяется схемой; не собрался — генерация останавливается, файлы не пишутся;
6. профиль сериализуется в TOML в порядке разделов, без внешних зависимостей.

`unknowns` остаются в профиле: генератор не выдумывает значения ради заполненного документа.

## 3. Рендер документов

Все документы манифеста рендерятся одним проходом. Ссылки считаются от пути текущего документа, команды берутся из `tests.commands`, отсутствующая роль печатается как «гейтов нет».

Путь результата подставляется из манифеста (`{docs.dir}`) и проверяется: файл не может оказаться вне каталога проекта. Сначала рендерятся все документы в памяти, потом пишутся файлы — ошибка шаблона не оставляет половину набора.

## 4. Фрагменты адаптера

`docs_fragments` указывает `target`, `marker` и `content`. `target` — идентификатор документа, его путь или путь относительно каталога документов; совпадение должно быть ровно одно. `marker` — `adapter:<имя>`, маркеры `generated:` адаптеру недоступны.

| Ситуация | Поведение |
|---|---|
| адаптер дал содержимое | оно вставляется между маркерами |
| адаптер дал пустую строку | маркеры остаются пустыми |
| адаптера нет, а маркер есть в готовом файле | прежнее содержимое сохраняется |

Сохранение — причина, по которой повторный запуск не стирает ручную работу. Заголовки и подстановки внутри фрагмента запрещены: их проверяет рендерер.

## 5. Сгенерированные фрагменты

| Маркер | Источник |
|---|---|
| `generated:canon` | таблица K из `canon/registry.md` |
| `generated:adapter` | `rules` адаптера |
| `generated:project` | `rules` профиля |
| `generated:no-gate` | строки K, A и P с меткой «нет гейта» |
| `generated:rules` | короткий список всех трёх пространств для `AGENTS.md` |
| `generated:baseline` | строки `baseline.toml` |
| `generated:features` | файлы `{docs.dir}/features/*.md`: H1 и путь |

`debt` и `incidents` остаются пустыми: источника данных пока нет. Пустая таблица удаляет раздел целиком — это видимый пробел, а не тишина. Файлы функций создаются отдельно и не перезаписываются: индекс собирается из них.

## 6. Правила K, A, P

| Пространство | Где живёт | Кто проверяет |
|---|---|---|
| K | `canon/registry.md` набора | загрузчик канона |
| A | `rules` адаптера | `ai_kit/rules.py` |
| P | `rules` профиля | схема профиля и `ai_kit/rules.py` |

У строки обязательны номер своего пространства, формулировка, метка, исполнитель, кто ловит, владелец и триггер. Для «нет гейта» дополнительно нужна причина и триггер, отличный от «—»; для гейта исполнитель не может быть «—»; для дисциплины и измерителя нужен тот, кто ловит.

Канон читается из таблицы раздела «Канон (K)»; строки адаптера и профиля — структуры, а не текст. Это единственное место, где набор разбирает Markdown: реестр канона — источник, и его формат проверяется при загрузке.

## 7. Безопасность, повторный запуск, коды возврата

- запись только внутри каталога проекта; `--write-profile` с выходом наружу — ошибка;
- `--dry-run` рендерит всё, но не пишет ни одного файла;
- `--ask` спрашивает только неизвестные слоты батча: строка, список, `y/n`, роли команд, имя факта для доказательства; пустой ввод — «неизвестно»;
- после `--ask` показывается число документов и запрос подтверждения; `--yes` пропускает подтверждение;
- команды из адаптера заполняют пропущенные роли в `tests.commands`, значения профиля и ответов имеют приоритет;
- `detect` проверяется: форма и относительность масок; `doctor` предупреждает, если ни одна маска не находит файл. Выбор адаптера остаётся явным;
- всегда создаётся `baseline.toml` (если его нет): принятые нарушения с правилом, местом, причиной, владельцем и триггером. Файл пишется после рендера, поэтому в первом прогоне таблица baseline пуста: строки добавляются в файл и обновляются через `--refresh`;
- при `pre_commit = true` создаются `tools/pre-commit.py` и `tools/hooks/pre-commit` с ролями `unit` и `lint` (или `test`, если их нет); команды хранятся списком аргументов, хук ищет рабочий `python3`/`python`/`py -3`, `.bat`/`.cmd` запускаются через `cmd /c`. Если PATH не помогает, задаётся `git config hooks.interpreter <путь>` или `AI_KIT_PYTHON`;
- `--refresh` перерисовывает документы по существующему профилю: обновляет `generated:`-фрагменты, карту функций и baseline, не меняя профиль и не создавая артефакты;
- уже существующие файлы перечисляются в отчёте как перезаписанные: `README.md`, `AGENTS.md` и документы манифеста;
- повторный запуск на тех же входах даёт те же файлы: сгенерированные фрагменты детерминированы, ручные — сохраняются;
- коды возврата: `0` — успех, `1` — данные или шаблон не прошли проверку, `2` — ошибка использования.

```text
python -m ai_kit.init --profile profile.toml --adapter adapter.toml --answers answers.toml
python -m ai_kit.init --answers answers.json --dry-run
python -m ai_kit.init --ask
python -m ai_kit.init --ask --yes
python -m ai_kit.init --refresh --profile profile.toml --adapter adapter.toml
python -m ai_kit.init --profile profile.toml --adapter adapter.toml --write-profile docs-profile.toml
```

Команда запускается из каталога проекта; набор должен быть доступен интерпретатору (`PYTHONPATH` на каталог `ai-kit`). Шаблоны и канон читаются из набора, результаты пишутся в текущий каталог.

## 8. Границы шага

- генератор не доказывает факты: пробы и ответы — шаг интервью;
- не запускает команды, гейты и миграции;
- не создаёт адаптер и не угадывает стек;
- не заполняет карту функций, техдолг и журнал сбоев: у них нет источника данных;
- не решает вопрос зрелости проекта: состояния «новый», «развивающийся» и «развивающийся с документацией» пока не различаются.
