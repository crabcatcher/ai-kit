# Интервью и пробы

Шаг 5 плана. Документ описывает, как набор получает факты о проекте: пробы читают файлы, вопросы закрывают то, что файлами не доказано. Реализация — `ai_kit/interview.py`, схема профиля — `ai_kit/profile.py`.

## 1. Задача

У факта три состояния, четвёртого нет:

| Состояние | Как получено | Провенанс |
|---|---|---|
| доказан | проба нашла файл и значение | `probe` |
| назван человеком | ответ на вопрос | `answer` |
| неизвестен | пробы не нашли, человек не ответил | `unknown` |

«Вероятно» и «обычно так бывает» — не состояние. Версия заполняется только из `probe` и только вместе с путём-доказательством; версия из ответа превращается в `unknown` с вопросом.

Пробы выполняются до вопросов: спрашивать то, что уже доказано, запрещено. Батч строится заново после проб.

## 2. Банк вопросов

Универсальный банк — `interview/questions.toml`, не больше двенадцати вопросов. Адаптер добавляет свои — не больше пяти. После дедупликации — не больше пятнадцати.

| Поле | Требование |
|---|---|
| `id` | уникален в банке |
| `question` | непустая формулировка |
| `slots` | непустой список путей профиля; путь есть в схеме |
| `why` | зачем вопрос: без причины вопрос не задаётся |

Слот принадлежит ровно одному вопросу. Вопрос с несколькими слотами задаётся целиком, если хотя бы один слот неизвестен; остальные слоты после ответа считаются известными, а не «спрошенными повторно».

Дедупликация снимает вопросы адаптера по двум причинам: идентификатор уже есть или хотя бы один слот уже закрыт универсальным вопросом. Снятые вопросы перечисляются в отчёте проверки — молчаливого выбрасывания нет.

Поля «по умолчанию» нет: неизвестность выражается статусом ответа, а не значением по умолчанию.

## 3. Пробы

| Поле | Смысл |
|---|---|
| `id` | идентификатор пробы; уникален |
| `globs` | где искать; непустой список масок |
| `field` | поле профиля, которое заполняется |
| `extract` | правило извлечения |
| `name` | имя факта; обязательно для поля-доказательства, запрещено для остальных |
| `provenance` | всегда `probe`: проба — это данные, а не утверждение |

Маски относительные, с прямым слэшем: без `/` в начале, без буквы диска, без `..`, без обратного слэша. Файл читается, только если лежит внутри корня проекта; символическая ссылка наружу не даёт доказательства.

Порядок обхода детерминирован: маски и найденные файлы сортируются, побеждает первый файл с найденным значением. Файл больше 2 МиБ, нечитаемый или не в UTF-8 пропускается с причиной.

| Правило извлечения | Что делает |
|---|---|
| `json:<путь>` | разбирает JSON и идёт по пути через точки; индекс списка — числом |
| `toml:<путь>` | то же для TOML |
| `regex:<выражение>` | первая группа; без групп — всё совпадение |

Проба не выполняет команды и не пишет файлы: только чтение. Не нашла — возвращает причину: файлы не найдены, значение не найдено, файл больше предела, маска не разбирается.

## 4. Применение проб

Скалярный слот проверяется по схеме и заполняется значением пробы. Две пробы на один скалярный слот — ошибка: какая из них права, решать не набору.

Поле-доказательство получает запись:

```toml
{ name = "runtime", version = "9.1", evidence = "manifest.json", provenance = "probe" }
```

`evidence` — путь относительно корня проекта в форме posix. Две пробы на один факт в одном запуске — ошибка: какая из них права, решать не набору. Запись с тем же именем в готовом профиле заменяется свежим доказательством, поэтому повторный запуск не ломается и не копит дубли.

## 5. Ответы человека

Ответ — файл TOML со списком `answer`. Поля: `slot`, `status`, `value`, `name`, `version`.

| Ситуация | Что в ответе | Что происходит |
|---|---|---|
| обычный слот | `value` по типу схемы | значение проверяется и записывается |
| слот-доказательство | `name` | запись с провенансом `answer`, версия остаётся неизвестной |
| человек не знает | `status = "unknown"` | слот уходит в неизвестные с вопросом |
| слот уже доказан | любой ответ | ответ игнорируется, побеждает проба |

У доказательства `value` запрещено: версия приходит только из файла. Если человек назвал версию, она не записывается — появляется отдельный вопрос «подтвердите файлом-доказательством». Ответ на слот, которого нет ни в одном вопросе банка, — ошибка: набор не принимает ответов на несуществующие вопросы.

Структурные слоты (таблицы и списки) принимают значение целиком: обязательные поля проверяются по схеме, лишние — ошибка.

## 6. Что считается неизвестным

Неизвестность собирается из трёх источников:

1. слоты заданных вопросов, на которые не ответили;
2. ответы со статусом `unknown`;
3. пробы, которые не нашли значение, — с причиной пробы.

Список дедуплицируется по полю. Запись, чьё поле стало известным после ответа, удаляется: например, проба не нашла рантайм, человек назвал его — вопрос о рантайме закрыт, но вопрос о версии остаётся.

У каждой записи есть `field` и `question`: «неизвестно» без вопроса — не результат.

## 7. Отчёт

| Что | Сколько |
|---|---|
| фактов подтверждено (`probe`) | записи с провенансом `probe` |
| фактов получено ответом (`answer`) | записи с провенансом `answer` |
| вопросов задано | размер батча |
| ответов получено | ответы, записавшие значение |
| ответов проигнорировано | ответы на уже доказанные слоты |
| осталось неизвестным | длина списка неизвестных |
| отключённых гейтов с триггером | строки `gates.disabled` |

После таблицы — перечень неизвестных полей. Отчёт не заменяет вопросы: поле без значения перечисляется, даже если вопрос уже задан.

## 8. Команды и коды возврата

```text
python -m ai_kit.interview --check [--adapter <путь>]
python -m ai_kit.interview --plan [--project <путь>] --profile <путь> --adapter <путь>
python -m ai_kit.interview --plan [--project <путь>] --profile <путь> --adapter <путь> --json
python -m ai_kit.interview --report [--project <путь>] --profile <путь> --adapter <путь> --answers <путь>
```

`--check` проверяет банк и пробы адаптера, печатает число вопросов, проб и снятых дублей. `--plan` выполняет пробы и печатает батч; с `--json` — машиночитаемый план. `--report` применяет ответы и печатает отчёт.

Банк вопросов читается из каталога стартера, пробы — из проекта: `--project` задаёт проект, по умолчанию текущий каталог. Поэтому команды работают из каталога проекта. Команды адаптера применяются до батча: роль, уже закрытая адаптером, не спрашивается.

Коды возврата: `0` — успех, `1` — данные не проходят проверку, `2` — ошибка использования.

### Машиночитаемый план

`--json` отдаёт:

- `probes.hits` — найденные факты: поле, имя, значение, путь-доказательство;
- `probes.misses` — промахи с причиной;
- `questions` — только вопросы батча, у каждого слоты с типом.

Слот-доказательство помечен `"evidence": true` и `"answer": "name"`: агент спрашивает имя факта, версию не придумывает. Для массива указан тип элементов, для объекта — свойства или `additional`.

Ответы принимаются и в JSON: файл с суффиксом `.json` разбирается как `{"answer": [...]}` с теми же полями, что TOML. Агент читает план, задаёт вопросы, пишет `answers.json` и запускает генератор.

## 9. Границы шага

- набор не пишет профиль: он возвращает значения и отчёт, запись профиля — шаг генератора;
- пробы не запускают команды и не меняют файлы;
- адаптера может не быть: универсальные вопросы работают, стек остаётся неизвестным;
- выбор технологий и формулировки стековых вопросов живут в адаптере, не в ядре.
