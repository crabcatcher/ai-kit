# Промпт: инициализация проекта

Файл для копирования в агента, которого запускают **из каталога проекта**. Путь к стартеру агент получает в запросе. Ничего в проекте до чтения этого файла менять не нужно.

## Что подставить

| Место | Значение |
|---|---|
| `<ПУТЬ_К_AI_KIT>` | каталог стартера на машине, где запускается агент; в документы не записывается |
| проект | текущий каталог агента |

Если стартер не установлен, установи его editable (`python -m pip install -e <путь из таблицы>`) или задай `PYTHONPATH` на этот каталог.

Если промпт передан ссылкой на этот файл, путь к стартеру можно не подставлять: он выводится из расположения файла (`docs/` → двумя уровнями выше).

## Промпт

```text
Ты инициализируешь документацию проекта по стартеру ai-kit.

Стартер: <ПУТЬ_К_AI_KIT>
Проект: текущий каталог.

Если путь назван в сообщении — используй его. Если не назван, но этот файл лежит в `docs/` стартера — стартер это каталог двумя уровнями выше. Если путь нельзя вывести или каталог недоступен — остановись и скажи: «Не указан путь к стартеру ai-kit. Укажите каталог стартера; без него инициализацию не начать». Не ищи стартер по диску, не подставляй похожий путь и не начинай правки.

`unknown` не заменяет обязательные поля профиля; `not_applicable` для обязательного поля запрещён. Минимальный набор — в `docs/generator.md`. Если их нет, спроси или остановись; не подставляй значения.

Цель: довести документацию до состояния, когда она описывает этот проект, а не шаблон. Стек и назначение проекта неизвестны заранее — их надо доказать файлами или получить ответом. Ничего не выдумывать. В стек проекта входят язык, фреймворки, хранилища и инструменты. Операционная система, версия интерпретатора или агента, локальные пути и окружение машины — не стек проекта и в документы не попадают: проект переносимый.

Стартер описывает бэкенд-часть проекта. В репозитории может быть и фронтенд (старый монолит, монорепозиторий): тогда описывай только серверную часть, а клиентские каталоги, экраны и сборку оставь вне документов. Остановись и скажи: «ai-kit не предназначен для клиентских приложений», только если бэкенда в проекте нет вовсе. Не адаптируй шаблоны под UI и не добавляй клиентские поля в профиль.

Все команды ниже — `ai-kit ...`. Если пакет не установлен, установи его editable или задай `PYTHONPATH` на каталог стартера.

Сначала прочитай в стартере:
- interview/agent-brief.md
- docs/interview.md
- docs/question-style.md
- docs/generator.md
- docs/doctor.md
- docs/adapter-contract.md

Работай по шагам.

1. Разведка, только чтение.
Найди манифесты зависимостей, лок-файлы, каталоги исходников, конфигурацию проверок, CI, схему хранения, точки входа, существующую документацию. Составь таблицу фактов: факт, где найден, путь-доказательство, провенанс probe. Неочевидная архитектура — по `docs/question-style.md`: типовое для стека, иначе дефолт из того же документа. Границы не выводи из отсутствия каталогов: это решения, а не инвентаризация того, чего нет.

2. Безопасность.
Если в проекте есть README.md, AGENTS.md или каталог документации, создай worktree или ветку и работай там. init перезаписывает README.md и AGENTS.md. Не коммить, не пушить, не читать .env и секреты, не запускать миграции и команды, пишущие в данные.

3. Входы.
Создай `.pilot/` только для плана и ответов и сразу добавь `.pilot/` в `.gitignore` проекта. Если `.gitignore` менять нельзя — в `.git/info/exclude`.
Источник документации — `<каталог документов>/source/`: он отслеживается в git и в `.gitignore` не попадает (ниже каталог документов — `.ai`):
- `.pilot/base.toml` — минимальный профиль: schema_version = "1" и docs (язык ru, каталог `.ai` рекомендуется, `.project` — дефолт);
- `.ai/source/adapter.toml` — адаптер под стек: detect, probes, commands, inputs, rules, gates, questions, docs_fragments. Только то, что реально подтверждается файлами. Версии — только probe с evidence. Нет гейта — не выдумывай его. Длинный markdown для `docs_fragments` выноси в отдельный файл рядом с адаптером и подключай через `content_file`;
- профиль после генерации — `.ai/source/profile.toml`, он тоже отслеживается.
Если `docs.dir` отличается от `.ai`, замени `.ai/source` на `<docs.dir>/source`.
Проверь адаптер:
  ai-kit adapter validate --adapter .ai/source/adapter.toml --profile .pilot/base.toml --probes

4. Интервью.
Получи машиночитаемый батч для себя:
  ai-kit interview --plan --profile .pilot/base.toml --adapter .ai/source/adapter.toml --json
Человеческую анкету собери по `docs/question-style.md`: там формула, примеры и запрет на машинные поля. Не показывай мне JSON, слоты и типы. Если ответ — один из предложенных вариантов (да/нет, «подходит/поправить», подтверждение корней или ролей), дай выбрать окном выбора харнесса или нумерованным списком, а не заставляй печатать. Ответы сохрани в .pilot/answers.json (или answers.toml). Если поле осознанно неприменимо — `status = "not_applicable"` с причиной; «нет» в строковом поле решением не является.

5. Генерация.
  ai-kit init --profile .pilot/base.toml --adapter .ai/source/adapter.toml --answers .pilot/answers.json --write-profile .ai/source/profile.toml
Если профиль не собрался — покажи ошибку и чего не хватает, не подставляй догадки.

6. Проверка и дозаполнение.
Прочитай сгенерированный план документации (post-init.md) и иди по майлстоунам M0–M8:
- заполняй adapter:-фрагменты в `.ai/source/adapter.toml`, а не в готовых документах: слои и зависимости, решения, именование, окружение, области коммитов, доступы, границы агента, форму инцидента. Длинный текст — файлом через `content_file`. Для таблиц в `features/<имя>.md` используй `target = "features/<имя>.md"`: файл создаётся вручную, меняются только adapter-маркеры. Если раздел уже удалён рендером, верни его через шаблон и `--refresh`, а не правь документ вручную;
- для каждого публичного входа (HTTP, CLI, событие, экспортируемая функция) создай файл функции в features и строку в карте функций; перечисли входы в `inputs` профиля, каждый `id` — в «Контрактах» одного файла;
- после создания или изменения features и baseline обнови только сгенерированные фрагменты: `ai-kit init --refresh --profile .ai/source/profile.toml --adapter .ai/source/adapter.toml`. Профиль при этом не меняется. Перед `--refresh` покажи diff: документы перерисовываются, ручные правки вне маркеров не сохраняются — переноси их в `docs_fragments`;
- добавь правила проекта P в rules профиля;
- существующие нарушения — в baseline.toml с владельцем и триггером; новый код baseline не расширяет;
- pre-commit включай только если я подтвердил; после включения поставь `git config core.hooksPath tools/hooks`; если хук не находит интерпретатор, задай `git config hooks.interpreter <путь>`;
- гейты запускай с --gates; недоступный инструмент — пробел с владельцем и триггером; код 3 — не успех;
- после каждого майлстоуна показывай: что изменено, критерий выполнен, команда проверки.

Не удаляй существующие документы. Если старый документ расходится с новым — покажи diff и спроси, что оставить.

7. Приёмка.
В конце покажи:
- вывод doctor (0 ошибок; пробелы объяснены);
- git status --short;
- какие майлстоуны закрыты и чем;
- что осталось открытым и какой вопрос нужен от меня.

Ограничения: не коммить, не пушить, не читать секреты, не выходить за каталог проекта без запроса. Повторный init — только после согласования. Не записывай в профиль, adapter, baseline и документы локальные пути (диск, домашний каталог, temp): только пути внутри проекта, относительные. Путь к стартеру — параметр запуска, а не факт проекта.
```

## Если проект уже инициализирован

Не запускай `init` заново. Начни с `doctor` и `post-init.md`, затем продолжай с первого открытого майлстоуна. Повторная генерация допустима только после согласования: она перезапишет шаблонные части документов.
