# Брифинг: агент поднимает набор документов

Ты поднимаешь документацию проекта по набору `ai-kit`. Результат работы — не «красивые документы», а профиль с доказанными фактами, набор документов из шаблонов и отчёт о том, что подтверждено, что спрошено и что осталось неизвестным.

## Карта разделов

| Раздел | О чём |
|---|---|
| Порядок | шаги до генерации |
| Что считается доказательством | факт и его источник |
| Обязательные правила | что обязательно |
| Если доступа к репозиторию нет | режим без проб |
| Архитектура схематично | минимум для architecture |
| После инициализации | что доделать после `init` |
| Отчёт в конце | числа и неизвестные |
| Чек-лист перед сдачей | приёмка |

## Порядок

1. **Разведка (только чтение).** Найди манифесты, каталоги исходников, конфигурацию проверок, схему хранения, файлы непрерывной проверки, существующую документацию.
2. **Таблица фактов.** Для каждого факта: что нашёл, где искал, путь-доказательство, провенанс.
3. **Профиль.** Заполни `profile.toml` только из таблицы.
4. **Вопросы.** Человеческая анкета — строго по `docs/question-style.md`. Не показывай слоты, типы и JSON-план — он только для тебя. Машиночитаемый батч — `interview --plan --json`; ответы — `answers.json` с теми же полями, что TOML.
5. **Генерация.** Собери документы из шаблонов генератором (`docs/generator.md`); фрагменты адаптера — только между маркерами, ручное содержимое маркеров сохраняется.
6. **Проверка.** Прогони валидатор и покажи отчёт.

## Что считается доказательством

| Факт | Где искать | Провенанс |
|---|---|---|
| версия языка и фреймворков | манифест и лок-файл зависимостей | `probe` |
| каталоги исходников | структура репозитория | `probe` |
| команды проверок | манифест, конфигурация проверок | `probe` |
| хранилище и его версия | конфигурация подключения, схема | `probe` |
| непрерывная проверка | файл конвейера | `probe` |
| назначение проекта | документация, описание репозитория | `answer` |
| границы проекта | человек | `answer` |
| слои и зависимости | структура каталогов и импорты | `probe` или `answer` |

Версия заполняется **только** из `probe` и только с путём-доказательством. Версия, названная человеком, — не факт: это `unknown` плюс вопрос.

Пробу выполняет адаптер автоматически или агент вручную — провенанс определяется доказательством, а не способом. Прочитал манифест и указал путь — `probe`; услышал от человека — `answer`.

## Обязательные правила

- Ничего не выдумывать. Нет доказательства и нет ответа — `unknown`, а не «вероятно».
- Не заполнять версию из памяти, из названия проекта или из «обычно так бывает».
- Факт, прочитанный агентом из файла, — `probe`, а не `answer`. Если проба не оформлена, оставь `unknown`; `answer` — только ответ человека.
- ОС, версия интерпретатора или агента, локальные пути и окружение машины — не стек проекта; в документы попадают только язык, фреймворки, хранилища и инструменты.
- Рабочий каталог `.pilot` сразу попадает в `.gitignore` проекта или в `.git/info/exclude`; входы и черновики не коммитятся.
- Вопросы — по-человечески: 3–5 за сообщение, с примером и форматом ответа; без слотов, типов и JSON-плана в чате. «Не знаю» — допустимый ответ и уходит в `unknowns`.
- Если человек не понял вопрос — переформулируй с примером, не повторяй тот же текст.
- Не описывать архитектуру, которой нет. Если слоёв нет — так и записать: «границы не зафиксированы».
- Границы — только решения о том, что не входит и где решается вместо проекта. Не выводи их из отсутствия каталогов и не перечисляй, чего в репозитории нет.
- Названия технологий живут в профиле и адаптере, не в ядре.
- Не удалять секции шаблона «на потом»: пустая секция — видимый пропуск, её надо закрыть фактом или вопросом.

## Если доступа к репозиторию нет

- попроси пути манифестов и каталогов, не угадывай;
- заполни только то, что сказал человек, с провенансом `answer`;
- всё остальное — в `unknowns` с конкретным вопросом;
- в отчёте скажи прямо: «пробы не выполнялись, факты о стеке не подтверждены».

## Архитектура схематично

Даже без деталей архитектура должна быть видна:

- назначение и границы;
- слои: имя, ответственность, от чего можно зависеть;
- направление зависимостей: только в разрешённую сторону, обратное ребро — нарушение;
- внешние системы: зачем и кто владеет контрактом;
- решения: что выбрали, почему, что отвергли;
- «что не разобрано» — обязательный раздел, а не признание провала.

Шаблон — `templates/architecture.md.tpl`. Неочевидная схема — по `docs/question-style.md`; предложение помечай как предложение, а не факт. Пустой раздел без причины не оставляй.

## После инициализации

Пока `unknowns` не пуст, документация не считается готовой. Полный план с критериями — `post-init.md` в каталоге документов проекта.

1. **Проверь базу.** `doctor` — 0 ошибок; каждое предупреждение и пробел объяснены.
2. **Закрой неизвестные.** По каждому полю: файл-доказательство (`probe`) или вопрос человеку (`answer`); обнови профиль и перегенерируй.
3. **Заполни `adapter:`-фрагменты.** Окружение, зависимости, именование, области коммитов, слои, внешние системы, решения, доступы, границы агента, форма инцидента, контракты и карта кода.
4. **Собери карту функций.** Файл `features/<имя>.md` по шаблону; контракты, «где в коде», нюансы. Индекс собирается из файлов командой `init --refresh`.
5. **Добавь правила проекта P.** Ветки, ревью, коммиты — строками `rules` профиля; перегенерируй реестр и `AGENTS.md`.
6. **Заполни baseline.** Существующие нарушения — `baseline.toml`: правило, место, причина, владелец, триггер. Новый код baseline не расширяет. После правок — `init --refresh`, чтобы строки появились в техдолге.
7. **Включи pre-commit.** Если `pre_commit = true`, проверь `tools/pre-commit.py` и `tools/hooks/pre-commit`; установи `git config core.hooksPath tools/hooks`. Если хук не находит интерпретатор — `git config hooks.interpreter <путь>`.
8. **Прогони гейты.** `doctor --gates`: недоступный инструмент — пробел с владельцем и триггером; код `3` — не успех.
9. **Сверь старые документы.** Не мержить слепо: вопрос зрелости проекта решается отдельно.
10. **Прими.** `doctor` чист, повторный запуск идемпотентен, ссылки живые, неизвестных без вопросов нет.

## Отчёт в конце

| Что | Сколько |
|---|---|
| фактов подтверждено (`probe`) | |
| фактов получено ответом (`answer`) | |
| вопросов задано | |
| осталось неизвестным | |
| отключённых гейтов с триггером | |

И одна строка: что из документов нельзя считать проверенным и почему.

## Чек-лист перед сдачей

- [ ] у каждого факта о стеке есть путь-доказательство;
- [ ] ни одной версии из `answer`;
- [ ] вопросы по-человечески: 3–5 за сообщение, с примером и форматом ответа, без слотов и типов;
- [ ] все неизвестные — с конкретным вопросом;
- [ ] слои либо подтверждены, либо явно названы не зафиксированными;
- [ ] фрагменты адаптера только между маркерами;
- [ ] валидатор прогнан, отчёт приложен.
